Engineering review · 2 Oct 2026 · TestPulse and six workspace repos

Verified Delivery Playbook

Your contracts and guardrails are stronger than most AI-built projects have. Your definition of done is the weak point. The agent that writes the code also signs it off, so unfinished work gets marked verified. This playbook keeps what works, replaces the role-play with independent checks and machine gates, and cuts the process context each session loads by about 85%.

Sources: git history, GitHub pull requests and Actions runs, and the files in each repo, all read on 2 Oct 2026. Token figures are file size divided by four. Gemini's plan is reviewed claim by claim in §3.

Is the persona method a good way to build?
Half of it is. The contracts are the valuable half: the master plan, ADRs, testable non-negotiables and CI gates. Keep them. The personas add ceremony without independence, because one model in one context plays every role. Turn them into on-demand knowledge, separate reviewer agents and machine gates.
Is Gemini's plan right?
It is right about independent review and about planning just in time. Most of the rest is already built, wrong for this repo, or based on numbers nobody measured. It never read your code or CI, so it missed the six real problems in §1.
What should change first?
Protect main, gate deploys on CI, and stop the agent from marking its own work done. That takes about three hours and closes the gap that every finding below came through.
Can the result be defect-free?
No process reaches zero. The reachable goal is no known defect at merge, fast detection after it, and every escaped defect turned into a gate so its class cannot ship twice.

§2 · Your method

Is the persona method a good way to build?

It is a strong planning system attached to a weak verification system. What makes TestPulse good is its contracts and its code-level guardrails. The personas add tokens and ceremony, and their sign-offs come from the same session that wrote the code.

Keep

  • The master plan as the canonical contract, with conflicts fixed in the same PR.
  • ADRs, and the pinned dependency baseline in ADR-004.
  • Non-negotiables phrased as testable rules: 404 across tenants, 403 for low roles, Zod at every boundary, no io.emit in handlers.
  • The guardrails already in code: ESLint boundary rules, strict TypeScript, the fail-closed MODEL_SCOPE tenant guard, schema-per-worker Postgres tests, real-Redis contract tests, gitleaks, the audit gate and commitlint.
  • FR and SC IDs in test titles.
  • The non-MVP exclusion list.

Retire

  • Reviewer sign-offs written by the session that wrote the code.
  • Scrum Master, Product Owner and DevOps role-play inside the agent. You are the product owner, and CI is the release manager.
  • Per-sprint test-case catalogs of 1,200–1,500 words and walkthroughs of about 1,000.
  • Hand-synced “Automated by” columns.
  • Detailed sprint files more than two slices ahead.
  • PRs that bundle several sprints.

Transform

  • Role skills become on-demand knowledge, loaded when a task touches that area.
  • Reviewer personas become separate agents with fresh context and a duty to show proof.
  • Prose rules become machine gates wherever a machine can check them.
  • task.md becomes a 40-line now-and-next board. History lives in git.
  • Traceability by label becomes traceability by behavior, with the scenario table generated from passing tests.

Why role-play gives no independence

A reviewer persona inside the builder's session reads the builder's reasoning first. It inherits the same assumptions, the same reading of the spec and the same blind spots. Independence needs four things the persona setup lacks.

  • A fresh context that holds the spec and the diff, and none of the builder's narrative.
  • A different objective: find what is wrong and prove it.
  • The means to run things, such as tests, the app and CI logs.
  • Ideally a different model family. You already use Gemini in Antigravity and Claude in Claude Code. Build with one and review with the other.

Your setup is close to BMAD-METHOD and to MetaGPT-style software-company simulations. Their useful part is the structure they impose. Their weak spot is also the same, since they produce sign-offs without independent evidence.

In this Claude Code session, none of the twelve .agents/skills folders were registered as skills. They load only when a prompt names the file, which is why every sprint prompt lists them by path.

§4 · Alternatives

Five approaches that beat the current style

Ranked by how many defects each one keeps out of main. Each replaces a specific part of the persona workflow, and together they form the slice loop in §5. Unlike the matrix in Gemini's plan, the table below lists what each one costs.

1

Maker–checker verification

The agent that writes the code never decides it is done. A separate checker with a fresh context does, and it has to show proof. You make the merge call.

Today

Reviewer personas sign off inside the builder's own session, after reading the builder's own summary.

Proposed

Three reviewer agents run after the build in their own contexts. You approve the PR from an evidence table.

Why it beats the current style

A claims audit compares each acceptance criterion with the diff and the CI logs. It would have flagged findings 01 to 04 by reading alone. An adversarial pass with the ADR-005 checklist goes straight at 05 and 06.

How to set it up in TestPulse

  1. Add .claude/agents/claims-auditor.md, security-reviewer.md and test-auditor.md (§9). Each gets the slice brief, git diff origin/main...HEAD and the CI results. None sees the builder's conversation.
  2. Every finding carries severity, file:line and proof, which can be a failing test, command output or quoted code. A finding without proof is dropped.
  3. The builder fixes evidenced findings only, and each reviewer re-checks only what it raised.
  4. Review with a different model family from the builder. Build in Antigravity and review in Claude Code, or the other way round.
  5. Run the built-in /code-review and /security-review on the branch before opening the PR.
  6. Read the PR's evidence table and the diff of risky files yourself. Budget 10 to 15 minutes.

Tradeoffs

Reviewer contexts cost roughly 30–60k tokens on a risky slice. Skip the security reviewer on docs-only and purely visual slices. Reviewers make mistakes too, which is why the proof rule matters.

  • Defectslarge cut
  • Tokens+30–60k on risky slices
  • Speedabout even
2

Executable acceptance

Acceptance criteria become failing tests before any implementation starts. The builder makes them pass and may not edit them.

Today

Markdown catalogs and SC labels. The same session writes the tests after the code.

Proposed

Acceptance tests are the spec, and the scenario table is generated from them.

Why it beats the current style

Rate limiting, timing parity and concurrent refresh were all written down, and none was tested as behavior. A failing test cannot be marked done.

How to set it up in TestPulse

  1. Write criteria in EARS form, for example “When an account has 5 failed logins within 15 minutes, the API shall return 429 for that account from any IP.”
  2. Make the first step of every slice the acceptance tests: write *.acceptance.test.ts, run it, confirm each test fails for the right reason, and commit it as test(acceptance): ….
  3. Lock the spec. A PreToolUse hook blocks edits to committed acceptance tests (§9). If the spec is wrong, the agent stops and asks you.
  4. Require tests by risk.
    • Every tenant route gets a 404/403 matrix generated from a route inventory.
    • Every check-then-act gets a Promise.all concurrency test.
    • Pure logic gets fast-check property tests: tenant scope rules, fingerprinting, flaky scoring and quarantine transitions.
    • Auth timing gets a structural test that unknown emails still run argon2 against a dummy hash.
  5. Replace the hand-synced “Automated by” column with a script that builds it from passing test titles. Tests that only read config files move to test/meta/ and stop counting.
  6. Run Stryker weekly on three or four pure modules instead of the whole repo.

Tradeoffs

Each slice gets 15 to 30 minutes longer before code starts. You stop paying for rework, and the catalog stops drifting.

  • Defectslarge cut
  • Tokenslower, no per-sprint catalogs
  • Speedslower per slice, faster per feature
3

Process as code

Anything a machine can check is checked by a machine at the earliest point. Done means green required checks on a protected main and a passing smoke test on staging.

Today

AGENTS.md describes the gates, and the agent reports how they went.

Proposed

GitHub, CI and agent hooks enforce the gates. The agent cannot report its way past them.

Why it beats the current style

The coverage gate, the deploy gating and the skipped deploy steps existed only as prose. Two CI failures surfaced only after the agent had reported green.

How to set it up in TestPulse

  1. Protect main with required checks “Verify Quality Gates” and “Playwright E2E Smoke Tests”, up-to-date branches, linear history, no force pushes, and admins included (§9 F).
  2. Deploy only after CI succeeds, through workflow_run, with secrets at job level. On main, fail when a secret is missing instead of skipping. Add a smoke job that waits for staging to report the new commit and then runs a login check (§9 E).
  3. Set coverage thresholds in each Vitest config at today's values and only ever raise them. Vitest's coverage.thresholds.autoUpdate can write the new floor for you (§9 G).
  4. Fail PRs above 800 changed lines of product code, with the lockfile, generated code, migrations, tests and docs excluded, unless they carry a size/exception label with a reason (§9 I).
  5. Add one npm run verify that runs what CI runs, in CI order.
  6. Add Claude Code hooks that lint each edited file and stop the agent from ending a turn while lint or typecheck fails (§9 D).
  7. Flag stubs in src/ with no-restricted-syntax for void x; and no-warning-comments for TODO and FIXME (§9 J).
  8. Turn on CodeQL default setup, which automation-frameworks and buggy-books already run, and Dependabot or Renovate for updates.
  9. Adopt one rule: every escaped defect becomes a gate. Write the test, lint rule or check that would have caught it.

Tradeoffs

About half a day to set up. Branch protection with admins included also blocks you, which is the point. Keep the exception label for real emergencies.

  • Defectslarge cut for infra and drift
  • Tokenslower, rules leave the prompt
  • Speedfaster, less rework
4

Thin vertical slices, planned just in time

Plan by outcome and detail only the next one or two slices. Each slice crosses DB, API, events and UI, ships to staging, and stays small enough to review in 15 minutes.

Today

11 phases and 60 sprint files written up front. Polish waits for Phase 09 and quality engineering for Phase 10. Sprints get batched into PRs of 4,000 to 13,000 lines.

Proposed

An outcome roadmap (Now, Next, Later), one-page slice briefs, about 800 product lines per PR at most, and quality inside every slice.

Why it beats the current style

Nobody, human or agent, reviews a 5,000-line PR with rigor. Accessibility, coverage and security audits get more expensive the later they run. The sprint files for Phases 05 to 11 were written before any ingestion code existed.

How to set it up in TestPulse

  1. Write planning/roadmap.md with 6 to 8 outcome milestones. M1: a new user signs up, creates a project, gets an API key, runs the reporter and watches the run arrive live.
  2. Build M1 as a walking skeleton first, the thinnest path that works end to end on staging. Then deepen it.
  3. One slice is one agent session, one PR and at most about 800 product lines. Hide unfinished UI behind a flag.
  4. Every slice's definition of done includes axe checks, loading, empty and error states, isolation tests, and a performance budget where it applies. Phases 09 and 10 shrink to release work.
  5. Keep the master plan and the ADRs. Freeze the old sprint files as reference notes and stop maintaining them.
  6. Dogfood early. Once the reporter works, send TestPulse's own CI runs, and the AutomationFrameworks Playwright suites that run against BuggyBooks, into staging TestPulse. You get real flaky tests and real load at no cost.

Tradeoffs

About two hours to re-plan, and you give up the comfort of a complete plan. In return the plan stays true to the code.

  • Defectsmoderate cut, every PR reviewable
  • Tokenslower, smaller contexts
  • Speedfaster to working features
5

Context engineering

Load the smallest context that lets the agent do the next slice correctly. Everything else stays on disk until a task needs it.

Today

About 47.5k tokens of process docs per sprint, with personas pulled in by the prompt.

Proposed

About 7k tokens: a lean AGENTS.md, the slice brief, one or two skills on demand, and only the contract sections the brief cites.

Why it beats the current style

Long context dilutes attention. ADR-005 §9 was on the agent's reading list and was still missed. Every session re-reads the master plan, both catalogs and task.md whether or not the slice needs them.

How to set it up in TestPulse

  1. Cut AGENTS.md to about 1.5k tokens: commands, 8 to 10 one-line non-negotiables that each name their enforcing check, a repo map and the slice loop (§9 A).
  2. Move persona knowledge into skills with precise descriptions and copy them to .claude/skills/, so Claude Code loads them only when a task needs them.
  3. Add folder rules for apps/api, apps/web and packages/db. Keep them in AGENTS.md files for Antigravity, with a one-line CLAUDE.md beside each (@AGENTS.md) if your Claude Code version does not pick up nested AGENTS.md files.
  4. Slice briefs cite master-plan sections by heading. The agent reads those sections and nothing else from the plan.
  5. Replace walkthroughs and per-sprint catalogs with the PR description and one CHANGELOG line.
  6. Shrink task.md to a NOW.md of about 40 lines. History lives in git.
  7. Keep one slice per session. Start reviews in fresh sessions. Use an Explore subagent for codebase searches so the main thread stays small.
  8. Route models by task: the strongest model for design, risky code and security review, and a faster one for search, doc sync and the test audit.
  9. Record tokens per merged slice with the other metrics in §8.

Tradeoffs

About three hours once. Knowledge that leaves the always-on file has to stay findable, so each skill description must say exactly when to load it.

  • Defectsmoderate cut, rules get followed
  • Tokensabout 85% less process context
  • Speedfaster sessions
§5 · Operating model

The slice loop

One slice, one session, one PR. You spend about 20 minutes per slice at two checkpoints, where human judgment pays off most. The first is before any code, on the requirements. The second is before merge, on the evidence.

  1. 1

    Pick

    Choose the next slice from NOW.md.

    YouGate: none
  2. 2

    Brief

    The builder drafts a one-page brief: outcome, EARS criteria, non-goals, risks and cited contract sections.

    BuilderYouCheckpoint 1: you approve, 5–10 min
  3. 3

    Tests first

    Write the acceptance tests, watch them fail for the right reason, and commit them.

    BuilderGate: hook locks committed acceptance tests
  4. 4

    Build

    Implement in small commits. Each edit is linted as it lands.

    BuilderGate: Stop hook runs lint and typecheck
  5. 5

    Verify

    Run npm run verify locally, then CI runs on push.

    MachineGate: required checks
  6. 6

    Review

    Claims, security and test auditors run in parallel, each in a fresh context.

    CheckersGate: every finding needs proof
  7. 7

    Fix

    Fix the evidenced findings. Each reviewer re-checks only what it raised.

    BuilderGate: required checks again
  8. 8

    Merge

    Read the evidence table and the risky files, then merge.

    YouCheckpoint 2: your merge, 10–15 min
  9. 9

    Ship

    CI-gated deploy to staging, smoke test, dogfood telemetry.

    MachineGate: smoke must pass
  10. 10

    Learn

    Turn any escaped defect into a test, lint rule or check.

    BuilderGate: none

Where parallel agents help They help with the three reviewers, with codebase exploration, and with slices that share no files, such as the marketing site while ingestion is built, each in its own worktree. They hurt when two builders work one slice, or when parallel work touches schema.prisma, the lockfile or shared contracts.

Expect a slice to take 20 to 40 minutes longer than a sprint does today. Expect far fewer slices to be redone, and no status you need to doubt.

§7 · Tokens

Token budget

Main-thread process context drops by about 85%. Written ceremony falls from about 5.6k tokens per sprint (the P03-S02 catalog and walkthrough) to about 1k for a PR description and a CHANGELOG line. Reviewer agents add 30–60k tokens on risky slices, in their own contexts, so total spend per slice stays roughly flat at first. The difference is in what the tokens buy. They move from re-reading ceremony to finding defects. Prompt caching lowers the price of re-reads, but re-read text still fills the window and dilutes attention.

Keeping reviewer cost down

  • Run reviewers only on slices that touch auth, tenancy, ingestion, outbound calls or infrastructure.
  • Give reviewers the brief and the diff, never the whole repo.
  • Use a faster model for the test audit and for exploration.
  • Let machine gates go first. They cost no tokens.
